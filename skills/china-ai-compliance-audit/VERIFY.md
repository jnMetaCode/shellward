# 独立复核协议

复核员的任务只有一个：**证伪**。维持原判需要理由，推翻原判只需要一个反例。

## 给复核 agent 的输入

把下面这个模板**连同本文件的「复核清单」和「常见误报」两节**一起交给复核 agent。除此之外什么都不给——尤其不要给审计员的推理过程，那会让复核员顺着想。

```
项目根: <path>

记录 <F-xxx>
  控制项: <id> <title>
  控制项考察范围:
    - <controls.json 里该项的 look_for，逐条抄过来>
  命题: <gap|met> — <finding.title>
  取证:
    - <file>:<line> "<quote>"
    - <file>:<line> "<quote>"

（同一组文件的多条记录可以接着往下列）
```

并附上这段指令：

> 你是复核员，没有参与前面的审计。只读，不要改任何文件；**不要读 `.compliance/` 目录**（里面是审计员的推理，读了就不独立了）。
>
> 对每条记录：打开取证位置读上下文，尝试推翻**这个命题本身**。你只判断命题是否属实，**不判断整个控制项是否满足**——命题属实但范围比控制项窄，仍然是 upheld，可以在 note 里指出没覆盖到什么。
>
> 每条回答 upheld 或 overturned，并用一句话说明依据（带 文件:行）。对事实拿不准时回答 overturned。

## 复核清单

对 `gap`：

1. 引用的那一行现在还在吗？读上下各 30 行，不只看那一行。
2. 这段代码真的会执行吗？是不是测试、示例、脚手架、已注释、死代码、`if (false)`？
3. 别处有没有补偿措施？——上游中间件统一脱敏、网关层统一审核、基类里统一打日志。搜一遍调用链再下结论。
4. 数据真是个人信息吗？变量叫 `user` 不等于它含个人信息，看它的字段。
5. 严重度配得上吗？只发公开文本到境外模型，不该是 critical。

对 `met`：

1. 引用的措施覆盖所有路径吗？重试、降级、批处理、流式输出、管理后台常常绕过主路径。
2. 它是真的在做事，还是只有函数名像？打开实现读一遍——`sanitize()` 里只有一行 `return input` 的事发生过。
3. 配置值对吗？日志保留写了 30 天不满足 180 天的要求。

## 常见误报（审计员最容易踩的）

- 把 `.env.example`、`README` 里的示例 key、测试夹具里的假手机号当成真泄漏。
- 看到 `openai` 依赖就判数据出境——很多项目把 `baseURL` 指向了境内兼容端点。要看实际 base URL 从哪来。
- 因为**没找到**内容审核 / 鉴权 / 限流 / 日志保留配置就判 `gap`——它们可能在网关、云厂商或部署侧，仓库里看不到。这类写 `needs_human`。只有正面看到违规行为才是 `gap`（判别规则见 SKILL.md 阶段 2）。
- 「误报不是判得太严，是看的东西不完整。」下结论前先问：我是不是只看了一个文件？

## 记录

```json
"verifier": { "mode": "independent", "result": "upheld", "note": "chat.ts:41 之前无任何脱敏调用，重试路径 retry.ts:12 同样直发" }
```

被推翻的发现不要删：`verdict` 改为 `rejected`，`reason` 写复核员给的反例，去掉 `severity` 和 `verifier`。

`rejected` 不计入覆盖。如果一个控制项的记录因此全没了，回到阶段 2 给它补一条结论（多半是 `needs_human`）。复核员在 note 里指出「命题属实但没覆盖到 X」时，也为 X 补一条记录。
